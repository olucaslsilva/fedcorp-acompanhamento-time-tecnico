Semana 1: Refatoração, do "funciona" para o "bem feito"
Python / FastAPI
Objetivo: Pegar um código que funciona mas está bagunçado (tudo num arquivo só, nomes genéricos, lógica repetida) e reorganizar em módulos separados, com nomes claros e sem repetição.
1
Criar o repositório
No GitHub pessoal, criar o repositório fedcorp-exercicios e dentro criar a pasta semana-01-refatoracao/
2
Criar o código "bagunçado" (antes.py)
Criar uma API FastAPI de gerenciamento de produtos (criar, listar, atualizar, deletar) com TUDO em um único arquivo: validações repetidas, nomes genéricos como data e result, sem tipagem Pydantic, lógica de negócio misturada com rotas
3
Refatorar em módulos separados
Reorganizar o código em arquivos separados com responsabilidades claras:
schemas.py para modelos Pydantic (validação de dados)
routers/products.py para rotas HTTP
services/product_service.py para lógica de negócio
4
Escrever o decisoes.md
Criar um arquivo decisoes.md explicando: quais problemas você identificou no código original, o que mudou, e por que cada mudança melhora o código. Não basta dizer "separei em arquivos", tem que explicar por quê isso importa.
O que entregar no GitHub
  • semana-01-refatoracao/antes.py (o código original bagunçado)
  • semana-01-refatoracao/schemas.py (modelos Pydantic)
  • semana-01-refatoracao/routers/products.py (só rotas)
  • semana-01-refatoracao/services/product_service.py (só lógica)
  • semana-01-refatoracao/decisoes.md (explicação das escolhas)
Como vou avaliar
  • O código refatorado roda sem erro?
  • Cada arquivo tem UMA responsabilidade clara?
  • Os nomes de variáveis e funções são descritivos?
  • O decisoes.md explica o PORQUÊ, não só o QUÊ?
Se travar, pergunte ao ChatGPT: "Tenho uma API FastAPI com tudo em um arquivo só. Quais são os primeiros passos para refatorar em módulos separados?"
Recursos: Vídeo "Refactoring Python Code" de ArjanCodes (YouTube, ~20min). Pydantic docs, seção "Models"

Semana 1: TypeScript, do "sei usar" para o "domino"
React / TypeScript
Objetivo: Dominar 3 conceitos avançados de TypeScript que separam uso básico de domínio. Generics (tipos genéricos), Utility Types (atalhos de tipos), e Discriminated Unions (uniões discriminadas).
1
Criar o repositório
No GitHub pessoal, criar o repositório fedcorp-exercicios e dentro criar a pasta semana-01-typescript/
2
Criar api-types.ts
Interface Produto com: id, nome, preco, categoria, estoque (opcional), criadoEm (Date)
Derivar usando Utility Types: ProdutoCreate (sem id e criadoEm), ProdutoCard (só nome, preco, categoria), ProdutoUpdate (tudo opcional)
Função genérica buscarLista<T>(endpoint: string): Promise<T[]>
3
Criar api-response.ts
Tipo ApiResponse<T> usando discriminated union: sucesso (com dados do tipo T) OU erro (com mensagem e código)
Função tratarResposta<T>(response: ApiResponse<T>) que retorna os dados se sucesso, ou lança erro se falha
4
Escrever o decisoes.md
Explicar: por que usar Omit em vez de criar uma interface nova do zero? Quando usar Partial vs Pick? Qual a vantagem de generics em vez de funções separadas?
O que entregar no GitHub
  • semana-01-typescript/api-types.ts (interfaces, tipos derivados e função genérica)
  • semana-01-typescript/api-response.ts (discriminated union e função de tratamento)
  • semana-01-typescript/decisoes.md (explicação das escolhas)
Como vou avaliar
  • O código compila sem erro (tsc --noEmit)?
  • Usou Omit, Pick, Partial corretamente (não criou interfaces duplicadas)?
  • O generic <T> funciona com tipos diferentes?
  • O decisoes.md explica a diferença entre os utility types?
Se travar, pergunte ao ChatGPT: "Sou dev React com JS avançado, aprendendo TypeScript. Explique generics como se eu nunca tivesse visto, com um exemplo usando fetch de API."
Recursos: Vídeo "TypeScript Generics Tutorial" de Matt Pocock (YouTube, ~15min). TypeScript Playground (typescriptlang.org/play)

Semana 1: Code Review, a habilidade que você nunca praticou
Node.js / Fullstack
Objetivo: Aprender a ler código com olhar crítico ,identificar problemas de segurança, performance, clareza e boas práticas. Criar código intencionalmente ruim, fazer a review dele mesmo, e corrigir.
1
Criar o repositório
No GitHub pessoal, criar o repositório fedcorp-exercicios e dentro criar a pasta semana-01-code-review/
2
Criar o código "ruim" (para-revisar.ts)
Criar um endpoint Node.js/Express propositalmente cheio de problemas:
SQL injection (template string direto na query)
Sem validação de entrada
Sem tratamento de erro (sem try/catch)
Nomes genéricos (data, q, result)
Sem tipagem TypeScript (usar any)
Query ineficiente (buscar tudo do banco sem necessidade)
3
Fazer a review (review.md)
Criar um arquivo review.md onde você faz a review do seu próprio código:
Listar cada problema com severidade (crítico / importante / menor)
Explicar por que é um problema (qual o risco real se isso for pra produção)
Sugerir a correção específica para cada problema
4
Corrigir (corrigido.ts)
Reescrever o endpoint aplicando todas as correções: parameterized queries, validação, try/catch, nomes descritivos, tipagem completa
5
Escrever o decisoes.md
Diferente dos outros devs: além de explicar as escolhas técnicas, redefinir sua definição de "pronto" com critérios internos. Não mais "os superiores acharam bom", e sim "o que EU verifico antes de considerar algo pronto?" (tem teste? trata erro? tá documentado? nomes estão claros?)
O que entregar no GitHub
  • semana-01-code-review/para-revisar.ts (o código intencionalmente ruim)
  • semana-01-code-review/review.md (a review com problemas, severidades e correções)
  • semana-01-code-review/corrigido.ts (o código reescrito)
  • semana-01-code-review/decisoes.md (explicação + nova definição de "pronto")
Como vou avaliar
  • A review identificou pelo menos 5 problemas reais?
  • Cada problema tem severidade E explicação do risco?
  • O código corrigido resolve todos os problemas listados?
  • A nova definição de "pronto" tem critérios internos (não depende de aprovação externa)?
Se travar, pergunte ao ChatGPT: "Revise este endpoint Node.js/Express e me diga todos os problemas de segurança, performance e boas práticas que você encontra." Depois compare com a sua review.
Recursos: Vídeo "How to Do Code Reviews Like a Human" de Michaela Greiler (YouTube, ~20min). OWASP Top 10
