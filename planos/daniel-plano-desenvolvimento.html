3 Semana 1 — Code Review: A Habilidade que Você Nunca Praticou

Seu maior gap de processo • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Por que code review muda tudo?

No assessment, você marcou que nunca fez code review. Para alguém com seu nível técnico, esse é o gap mais impactante de resolver. Code review é a prática de ler o código que outra pessoa escreveu e dar feedback antes desse código ser integrado ao projeto. É assim que times profissionais garantem qualidade — e é também uma das formas mais rápidas de evoluir como dev.

Por que isso importa tanto para você especificamente:

  • Visibilidade — Você disse que sente que a empresa não reconhece seu trabalho. Code review é uma forma concreta de mostrar que você pensa em qualidade, que entende o código do projeto, e que contribui para a evolução do time. Quando você faz uma review bem feita, as pessoas percebem.
  • Aprender mais rápido — Quando você só escreve código, você vê o mundo de um ângulo só. Quando lê código de outra pessoa, descobre formas diferentes de resolver problemas. Às vezes melhores que as suas, às vezes piores — e aprender a diferenciar é o que te torna um profissional melhor.
  • Qualidade do projeto — Com review, bugs são encontrados antes de chegar em produção. Padrões do projeto são mantidos. Código confuso é simplificado. O resultado é um projeto mais estável e mais fácil de manter — e menos daquele sentimento de "apagar incêndio".

O que olhar em um code review (checklist mental):

  • Funciona? — O código faz o que deveria? Cobre os cenários normais e os edge cases? Se a API retornar erro, ele trata ou quebra silenciosamente?
  • Está claro? — Outro dev consegue entender sem perguntar pra quem escreveu? Os nomes de variáveis e funções são descritivos?
  • Está seguro? — Os dados são validados? Informações sensíveis estão protegidas? Tem SQL injection, XSS, ou credenciais hardcoded?
  • Tem testes? — Se é feature nova, tem teste? Se é bugfix, tem teste que impede o bug de voltar?
  • Está consistente? — Segue os padrões do projeto? Mesmo estilo, mesma estrutura, mesmas convenções?

Como dar feedback construtivo: Nunca diga só "isso está errado". Explique o que está errado, por que é um problema, e sugira uma alternativa. Em vez de "esse código tá ruim", diga "essa query sem índice vai ficar lenta com muitos registros — que tal adicionar um índice em user_id?".

Fase 2 — Exemplo Guiado: Revisando um endpoint Node.js

Imagine que um colega mandou esse código para review. Leia com calma e encontre os problemas antes de ver as anotações:

// endpoint enviado para review
app.post("/invoices", async (req, res) => {
    const data = req.body;                         // ← sem validação nenhuma
    const q = `INSERT INTO invoices (client, amount)
               VALUES ('${data.client}', ${data.amount})`;  // ← SQL INJECTION!
    await db.query(q);
    const all = await db.query("SELECT * FROM invoices");  // ← busca TUDO após inserir?
    res.json(all.rows);                            // ← sem status code, sem try/catch
});

Review que você faria:

  1. SQL Injection (CRÍTICO): A query usa template string com valores direto do req.body. Se alguém mandar client: "'; DROP TABLE invoices; --", apaga a tabela inteira. Sugestão: usar parameterized queries: db.query("INSERT INTO invoices (client, amount) VALUES ($1, $2)", [data.client, data.amount]).
  2. Sem validação: O endpoint aceita qualquer coisa no body. Se amount vier como texto ou negativo, vai pro banco sem nenhum filtro. Sugestão: validar campos obrigatórios e tipos antes de inserir.
  3. Sem tratamento de erro: Se o banco estiver fora, a aplicação crasheia. Sugestão: envolver em try/catch e retornar status 500 com mensagem de erro.
  4. Busca desnecessária: Depois de inserir uma nota, busca todas as notas do banco. Se tem 100.000 notas, isso trava a resposta. Sugestão: retornar só a nota criada com status 201.
  5. Nomes genéricos: data, q, all não dizem nada. Sugestão: invoiceData, insertQuery, createdInvoice.
// versão corrigida após a review
app.post("/invoices", async (req, res) => {
    try {
        const { client, amount } = req.body;

        if (!client || typeof client !== "string") {
            return res.status(400).json({ erro: "Campo 'client' é obrigatório" });
        }
        if (!amount || typeof amount !== "number" || amount <= 0) {
            return res.status(400).json({ erro: "Campo 'amount' deve ser um número positivo" });
        }

        const result = await db.query(
            "INSERT INTO invoices (client, amount) VALUES ($1, $2) RETURNING *",
            [client, amount]                        // ← parameterized query, sem SQL injection
        );

        res.status(201).json(result.rows[0]);       // ← retorna só a nota criada
    } catch (error) {
        res.status(500).json({ erro: "Erro interno ao criar nota fiscal" });
    }
});

4 Semana 2 — Testes Sistemáticos: De "às vezes" para "sempre"

Transformar hábito esporádico em prática profissional • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Você sabe testar. A questão é: quando e o quê?

Seu score em testes é 4, mas você marcou que testa "às vezes". Isso significa que você sabe escrever testes, mas não tem uma estratégia de quando e o que testar. O resultado é que os testes ficam no "quando dá tempo" — e quando dá tempo geralmente é nunca. Esta semana é sobre construir uma estratégia clara: o que sempre testar, o que pode pular, e como escrever testes que realmente protegem o projeto.

A regra dos 3 cenários obrigatórios:

Para qualquer função ou endpoint que você escrever, pelo menos esses 3 cenários precisam de teste:

  • Caminho feliz — A função recebe dados válidos e retorna o resultado esperado. Isso é o cenário normal, o que deveria acontecer na maioria das vezes. Exemplo: "passar um CPF válido para validarCPF() e ela retornar true".
  • Edge case — Uma situação incomum mas possível. Valor zero, lista vazia, texto com caracteres especiais, data no limite (31 de dezembro, 29 de fevereiro), string com espaços extras. Exemplo: "passar um CPF com pontos e traços (123.456.789-00) e ela ainda funcionar".
  • Cenário de erro — O que acontece quando algo dá errado? A função lança exceção, retorna mensagem de erro, ou falha silenciosamente? Exemplo: "passar um CPF com letras e a função retornar false em vez de crashear".

Quando NÃO testar (para não perder tempo):

  • Código que só passa dados adiante sem lógica (um controller que chama um service sem fazer nada além disso)
  • Código de terceiros (não teste se o Express funciona — a equipe do Express já fez isso)
  • Protótipos descartáveis que vão ser reescritos em breve
Fase 2 — Exemplo Guiado: Testando um service Node.js com Jest

Vamos testar um service que calcula o valor total de uma nota fiscal com impostos. Repare como cada teste cobre um dos 3 cenários obrigatórios:

// invoice.service.ts
interface InvoiceItem {
    descricao: string;
    quantidade: number;
    valorUnitario: number;
}

export function calcularTotal(itens: InvoiceItem[], aliquotaImposto: number): number {
    if (!itens || itens.length === 0) {
        throw new Error("Lista de itens não pode ser vazia");
    }
    if (aliquotaImposto < 0 || aliquotaImposto > 100) {
        throw new Error("Alíquota deve ser entre 0 e 100");
    }

    const subtotal = itens.reduce((acc, item) =>
        acc + (item.quantidade * item.valorUnitario), 0
    );

    const imposto = subtotal * (aliquotaImposto / 100);
    return Math.round((subtotal + imposto) * 100) / 100;
}
// invoice.service.test.ts
import { calcularTotal } from "./invoice.service";

// Cenário 1: caminho feliz
test("calcula total com imposto corretamente", () => {
    const itens = [
        { descricao: "Produto A", quantidade: 2, valorUnitario: 50 },
        { descricao: "Produto B", quantidade: 1, valorUnitario: 100 },
    ];
    // subtotal = (2*50) + (1*100) = 200 | imposto 10% = 20 | total = 220
    expect(calcularTotal(itens, 10)).toBe(220);
});

// Cenário 2: edge case — imposto zero
test("funciona com alíquota zero", () => {
    const itens = [{ descricao: "X", quantidade: 1, valorUnitario: 100 }];
    expect(calcularTotal(itens, 0)).toBe(100);  // sem imposto, subtotal = total
});

// Cenário 2b: edge case — valores com centavos
test("arredonda centavos corretamente", () => {
    const itens = [{ descricao: "Y", quantidade: 3, valorUnitario: 33.33 }];
    expect(calcularTotal(itens, 15)).toBe(114.99);  // 99.99 * 1.15 = 114.9885 → 114.99
});

// Cenário 3: erro — lista vazia
test("lança erro com lista vazia", () => {
    expect(() => calcularTotal([], 10)).toThrow("Lista de itens não pode ser vazia");
});

// Cenário 3b: erro — alíquota inválida
test("lança erro com alíquota negativa", () => {
    const itens = [{ descricao: "Z", quantidade: 1, valorUnitario: 100 }];
    expect(() => calcularTotal(itens, -5)).toThrow("Alíquota deve ser entre 0 e 100");
});

Perceba a estratégia: 5 testes, mas não são 5 aleatórios. Cada um cobre um cenário específico: dados normais, dados de borda (zero, centavos), e situações de erro. Com esses 5 testes, você tem confiança de que a função funciona corretamente — e se alguém mudar ela no futuro e quebrar algo, o teste avisa na hora.

5 Semana 3 — CI/CD: Do Git Push ao Deploy Automático

O gap que mais bloqueia devops • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: O que é CI/CD e por que muda o jogo?

Hoje, quando você termina uma feature, o que acontece? Provavelmente: você faz git push, alguém (ou você mesmo) entra no servidor e faz o deploy manual. Se der erro, alguém descobre depois — às vezes em produção. CI/CD automatiza tudo isso.

CI (Continuous Integration) significa que toda vez que alguém faz push, uma máquina automática roda os testes, verifica se o código compila, e avisa se algo quebrou. Você fica sabendo do problema em minutos, não em dias. É como ter um QA robô que trabalha 24 horas e nunca esquece de verificar nada.

CD (Continuous Delivery/Deployment) vai além: se os testes passaram e tudo está ok, o código é deployado automaticamente para o ambiente de staging ou produção. Sem ninguém precisar entrar no servidor, sem processos manuais que alguém pode esquecer ou errar.

O que um pipeline CI/CD básico faz, passo a passo:

  • Passo 1 — Checkout: A máquina baixa o código do repositório (a mesma coisa que um git clone, só que automático).
  • Passo 2 — Instalar dependências: Roda npm install para garantir que todas as bibliotecas estão presentes.
  • Passo 3 — Lint: Verifica se o código segue os padrões de estilo do projeto (indentação, nomes, etc.).
  • Passo 4 — Type check: Se é TypeScript, verifica se os tipos estão corretos (tsc --noEmit).
  • Passo 5 — Testes: Roda todos os testes automatizados. Se algum falhar, o pipeline para aqui e você é notificado.
  • Passo 6 — Build: Compila o código para produção.
  • Passo 7 — Deploy: Se tudo passou, publica automaticamente no servidor.

Cada passo é uma barreira de qualidade. Se qualquer um falhar, o código não avança. Isso garante que só código verificado chega em produção.

Fase 2 — Exemplo Guiado: Pipeline com GitHub Actions

GitHub Actions é a ferramenta de CI/CD do GitHub (que você já usa). Você cria um arquivo YAML no repositório e o GitHub executa automaticamente a cada push:

# .github/workflows/ci.yml
name: CI Pipeline

on:
  push:
    branches: [main, develop]     # roda quando faz push nessas branches
  pull_request:
    branches: [main]              # roda quando abre PR para main

jobs:
  quality:
    runs-on: ubuntu-latest        # roda numa máquina Linux gratuita do GitHub
    steps:

    - name: Checkout do código
      uses: actions/checkout@v4     # passo 1: baixa o código

    - name: Setup Node.js
      uses: actions/setup-node@v4
      with:
        node-version: 20

    - name: Instalar dependências
      run: npm ci                  # passo 2: instala exatamente o que está no lock

    - name: Type check
      run: npx tsc --noEmit        # passo 4: verifica tipos do TypeScript

    - name: Rodar testes
      run: npm test                # passo 5: roda todos os testes

    - name: Build
      run: npm run build           # passo 6: compila para produção

O que acontece na prática: toda vez que você fizer git push, o GitHub vai rodar esses passos automaticamente. Se qualquer um falhar, você recebe um email com o erro. Se tudo passar, um check verde aparece no commit e no PR. É assim que times profissionais garantem que código quebrado nunca chega em produção.

6 Semana 4 — Padrões de Projeto: Formalizando o que Você já Faz Intuitivamente

Dar nome e estrutura à experiência que você já tem • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Você já usa padrões. Só não sabe o nome deles.

No seu projeto de notas fiscais, você implementou semáforos e filas. Sabia que isso tem nome? Semáforo é um padrão de concorrência chamado "Semaphore". Fila é o padrão "Queue" (ou "Message Queue" quando usado entre sistemas). Quando você sabe o nome dos padrões, três coisas mudam: (1) você encontra documentação e exemplos mais rápido, (2) você consegue explicar suas decisões para outros devs sem precisar redesenhar a solução inteira, e (3) você sabe quando aplicar cada padrão em situações futuras.

3 padrões que todo fullstack precisa dominar:

  • Repository Pattern — Separar o acesso ao banco de dados da lógica de negócio. Em vez de escrever queries SQL diretamente dentro das rotas (como no exemplo da semana 1), você cria um arquivo separado que é o único responsável por falar com o banco. Se amanhã precisar trocar de PostgreSQL para outro banco, só muda o repository — o resto do código nem percebe. Você provavelmente já faz algo parecido quando separa queries em funções específicas — esse é o padrão.
  • Service Layer — Separar as regras de negócio das rotas HTTP. A rota só recebe a requisição e repassa para o service. O service aplica as regras (validações, cálculos, decisões). O repository salva no banco. Cada camada faz uma coisa só. Se precisar mudar uma regra de negócio, só mexe no service. Se precisar adicionar uma rota nova, só mexe no router. Ninguém pisa no pé de ninguém.
  • Error Handling Pattern — Ter uma forma consistente de tratar erros no projeto inteiro. Em vez de cada endpoint ter seu próprio try/catch com formatos diferentes de resposta, você cria um middleware de erro que padroniza tudo: sempre retorna { erro: mensagem, codigo: statusCode }. Quando algo dá errado em qualquer lugar, o erro é tratado de forma previsível — tanto para o frontend que consome quanto para você que debugga.
Fase 2 — Exemplo Guiado: Aplicando os 3 padrões juntos

Veja como fica um projeto organizado com Repository, Service, e Error Handling:

// errors/AppError.ts — erro padronizado do projeto
export class AppError extends Error {
    constructor(
        public message: string,
        public statusCode: number = 400
    ) { super(message); }
}

// repositories/invoice.repository.ts — SÓ fala com o banco
export class InvoiceRepository {
    async create(data: InvoiceCreate) {
        return db.query(
            "INSERT INTO invoices (client, amount, tax) VALUES ($1, $2, $3) RETURNING *",
            [data.client, data.amount, data.tax]
        );
    }
    async findById(id: number) {
        return db.query("SELECT * FROM invoices WHERE id = $1", [id]);
    }
}

// services/invoice.service.ts — SÓ aplica regras de negócio
export class InvoiceService {
    constructor(private repo: InvoiceRepository) {}

    async emitir(data: InvoiceCreate) {
        if (data.amount <= 0)
            throw new AppError("Valor deve ser positivo", 400);

        data.tax = calcularImposto(data.amount, data.tipo);
        return this.repo.create(data);         // ← service NÃO sabe SQL
    }
}

// routes/invoices.ts — SÓ recebe HTTP e repassa
router.post("/invoices", async (req, res, next) => {
    try {
        const result = await invoiceService.emitir(req.body);
        res.status(201).json(result);
    } catch (err) { next(err); }  // ← passa o erro pro middleware
});

// middleware/errorHandler.ts — trata TODOS os erros de forma padronizada
app.use((err, req, res, next) => {
    if (err instanceof AppError) {
        res.status(err.statusCode).json({ erro: err.message });
    } else {
        res.status(500).json({ erro: "Erro interno do servidor" });
    }
});

Perceba a separação: o router não sabe de SQL, o service não sabe de HTTP, e o repository não sabe de regras de negócio. Cada peça é independente. Se precisar trocar o banco, só muda o repository. Se precisar mudar regra de imposto, só muda o service. E o middleware de erro garante que qualquer falha retorna no mesmo formato — o frontend sabe exatamente o que esperar.

7 IA no Dia a Dia — Como Usar de Forma Inteligente

Você já usa ChatGPT e LLMs como ferramenta principal de resolução de problemas. Isso é bom — mas tem uma progressão para fazer isso de forma profissional, não apenas funcional.

1

Consumidor (Mês 1–2)

Você já está aqui. Usa IA para resolver problemas e tirar dúvidas. A evolução é aprender a dar contexto melhor para obter respostas melhores.

Exemplo: "Tenho um endpoint Express que insere no PostgreSQL. Quero adicionar tratamento de erro padronizado. Estou usando TypeScript."

2

Colaborador (Mês 3–4)

Você confronta as respostas da IA com documentação oficial (como já faz!) e identifica quando a sugestão é subótima. Exercícios incluem pedir a mesma coisa para 2 LLMs e comparar.

Exemplo: "O ChatGPT sugeriu usar callback para o semáforo, mas a documentação do Node mostra async/await com Mutex. Vou usar a abordagem mais moderna."

3

Diretor (Mês 5–6)

Você sabe quando não confiar no AI. Consegue identificar respostas desatualizadas, inseguras, ou ineficientes. Usa a IA para acelerar, não para substituir seu julgamento.

Exemplo: "O Claude sugeriu usar template literals na query SQL, mas isso abre SQL injection. Vou usar parameterized queries."

Regra de ouro:

Se você não consegue explicar por que o código que a IA gerou funciona, você ainda não entendeu. Volte ao fundamento e tente de novo.
