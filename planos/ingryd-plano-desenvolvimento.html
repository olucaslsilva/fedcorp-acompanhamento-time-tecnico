3 Semana 1 — TypeScript: De "sei usar" para "domino"

Solidificar a ferramenta que vai acompanhar toda sua evolução • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Por que TypeScript importa tanto?

Você já sabe JavaScript nota 5 e já usa TypeScript (nota 3). Então não vou te explicar o que é TypeScript — você já sabe. O que vamos trabalhar aqui é o salto de "uso básico" para "domínio". Quando você domina TypeScript de verdade, o editor vira seu melhor amigo: ele encontra bugs antes de você rodar o código, ele sugere autocomplete preciso, e ele impede que dados errados cheguem onde não deveriam.

Os 3 conceitos que separam uso básico de domínio:

  • Generics (tipos genéricos) — Imagine uma função que busca dados de uma API. Às vezes ela retorna um Usuário, às vezes um Produto, às vezes uma Lista de Pedidos. Em vez de escrever uma função diferente para cada tipo de dado, você escreve uma função só que aceita qualquer tipo. Generics são como um "espaço reservado" para o tipo — você define a função uma vez, e na hora de usar, diz qual tipo vai ser. É o equivalente a um molde de bolo: o molde é o mesmo, mas o sabor muda.
  • Utility Types (tipos utilitários) — O TypeScript vem com "atalhos" prontos para transformar tipos que você já tem. Por exemplo: você tem uma interface Usuario com 5 campos obrigatórios. Mas no formulário de edição, todos os campos são opcionais (o usuário pode mudar só o nome). Em vez de criar uma segunda interface do zero, você usa Partial<Usuario> e todos os campos viram opcionais automaticamente. Existem vários desses atalhos: Pick (pega só alguns campos), Omit (remove campos), Required (torna tudo obrigatório).
  • Discriminated Unions (uniões discriminadas) — Quando uma variável pode ser de tipos diferentes dependendo da situação. Por exemplo: uma resposta de API pode ser { status: "sucesso", dados: Usuario } ou { status: "erro", mensagem: string }. Com discriminated unions, o TypeScript sabe automaticamente quais campos existem com base no valor de status. Se status é "sucesso", ele sabe que dados existe. Se é "erro", ele sabe que mensagem existe. Sem isso, você teria que ficar fazendo if manual toda hora.
Fase 2 — Exemplo Guiado: Generics e Utility Types na prática

Vamos ver como esses conceitos funcionam em código real. Primeiro, uma função genérica que busca dados de API — repare que ela funciona com qualquer tipo de dado:

// Sem generics: uma função para cada tipo (ruim, muito código repetido)
async function buscarUsuario(id: number): Promise<Usuario> {
    const res = await fetch(`/api/usuarios/${id}`);
    return res.json();
}
async function buscarProduto(id: number): Promise<Produto> {
    const res = await fetch(`/api/produtos/${id}`);  // ← código igual, só muda o tipo!
    return res.json();
}

// Com generics: uma função que serve para qualquer tipo
async function buscar<T>(url: string): Promise<T> {  // ← T é o "espaço reservado"
    const res = await fetch(url);
    return res.json();
}

// Na hora de usar, você diz qual é o tipo:
const usuario = await buscar<Usuario>("/api/usuarios/1");  // retorna Usuario
const produto = await buscar<Produto>("/api/produtos/5");  // retorna Produto

Agora, Utility Types — transformando tipos que você já tem sem reescrever do zero:

interface Usuario {
    id: number;
    nome: string;
    email: string;
    avatar: string;
    cargo: string;
}

// Formulário de edição: todos os campos são opcionais
type UsuarioUpdate = Partial<Usuario>;
// Resultado: { id?: number; nome?: string; email?: string; ... }

// Card de preview: só precisa de nome e avatar
type UsuarioCard = Pick<Usuario, "nome" | "avatar">;
// Resultado: { nome: string; avatar: string; }

// Formulário de criação: tudo menos o id (o banco gera o id)
type UsuarioCreate = Omit<Usuario, "id">;
// Resultado: { nome: string; email: string; avatar: string; cargo: string; }

Perceba o ganho: você definiu a interface Usuario uma vez só, e derivou 3 variações sem repetir nenhum campo. Se amanhã adicionar um campo novo em Usuario, as variações se atualizam automaticamente.

4 Semana 2 — Testes de Componentes React

Transformar "testada" de conceito em hábito real • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Testar frontend é diferente de testar backend

Você disse no assessment que sua definição de pronto é "testada, funcional e documentada". Ótimo — mas no assessment você também marcou que seu nível de testes é "conhece o conceito". Isso significa que você sabe que testar é importante, mas ainda não transformou isso em prática do dia a dia. Esta semana é sobre fazer essa virada.

No frontend, testar é diferente do backend. No backend, você testa funções puras: "dou essa entrada, espero essa saída". No frontend, você testa comportamento: "quando o usuário clica nesse botão, o que acontece?", "quando a API retorna erro, o que o componente mostra?", "quando o formulário é enviado com campos vazios, o que aparece?".

As ferramentas que você vai usar:

  • Vitest — O framework de testes. Ele é quem roda os testes e diz se passaram ou falharam. É parecido com o Jest (que talvez você já tenha ouvido falar), mas é mais rápido e funciona melhor com projetos Vite/React modernos. Ele é o "motor" — quem executa tudo.
  • React Testing Library — A biblioteca que permite "simular" o que o usuário faz. Com ela, você pode renderizar um componente, encontrar um botão pelo texto, clicar nele, e verificar se algo mudou na tela. A filosofia dela é: teste como o usuário usa, não como o código funciona internamente.
  • O padrão AAA (Arrange, Act, Assert) — Todo teste segue 3 passos. Primeiro, você prepara o cenário (renderiza o componente com os dados que quer testar). Depois, você age (clica num botão, preenche um campo, dispara um evento). Por último, você verifica se o resultado é o esperado (o texto apareceu? o componente sumiu? a função foi chamada?).
Fase 2 — Exemplo Guiado: Testando um componente React

Vamos testar um componente simples de card de produto. Primeiro o componente, depois os testes:

// ProductCard.tsx — o componente que vamos testar
interface ProductCardProps {
    nome: string;
    preco: number;
    emEstoque: boolean;
    onComprar: () => void;
}

export function ProductCard({ nome, preco, emEstoque, onComprar }: ProductCardProps) {
    return (
        <div data-testid="product-card">
            <h3>{nome}</h3>
            <p>R$ {preco.toFixed(2)}</p>
            {emEstoque ? (
                <button onClick={onComprar}>Comprar</button>
            ) : (
                <span>Fora de estoque</span>
            )}
        </div>
    );
}
// ProductCard.test.tsx — os testes
import { render, screen } from "@testing-library/react";
import { userEvent } from "@testing-library/user-event";
import { ProductCard } from "./ProductCard";

test("mostra nome e preço do produto", () => {
    // Arrange: renderiza o componente com dados de teste
    render(<ProductCard nome="Camiseta" preco={59.9} emEstoque={true} onComprar={() => {}} />);

    // Assert: verifica se o nome e preço aparecem na tela
    expect(screen.getByText("Camiseta")).toBeInTheDocument();    // ← nome aparece?
    expect(screen.getByText("R$ 59.90")).toBeInTheDocument();     // ← preço aparece?
});

test("mostra botão de comprar quando tem estoque", () => {
    render(<ProductCard nome="Camiseta" preco={59.9} emEstoque={true} onComprar={() => {}} />);

    expect(screen.getByText("Comprar")).toBeInTheDocument();       // ← botão existe?
    expect(screen.queryByText("Fora de estoque")).not.toBeInTheDocument(); // ← aviso não aparece?
});

test("mostra 'Fora de estoque' quando não tem estoque", () => {
    render(<ProductCard nome="Camiseta" preco={59.9} emEstoque={false} onComprar={() => {}} />);

    expect(screen.getByText("Fora de estoque")).toBeInTheDocument(); // ← aviso aparece?
    expect(screen.queryByText("Comprar")).not.toBeInTheDocument();   // ← botão sumiu?
});

test("chama onComprar quando clica no botão", async () => {
    const onComprar = vi.fn();  // ← cria uma função "espiã" que registra se foi chamada
    render(<ProductCard nome="Camiseta" preco={59.9} emEstoque={true} onComprar={onComprar} />);

    // Act: simula o clique do usuário
    await userEvent.click(screen.getByText("Comprar"));

    // Assert: a função foi chamada exatamente 1 vez?
    expect(onComprar).toHaveBeenCalledTimes(1);                     // ← clique funcionou?
});

Perceba o que cada teste verifica: o primeiro testa se os dados aparecem na tela corretamente. O segundo testa o cenário "com estoque". O terceiro testa o cenário "sem estoque". O quarto testa se clicar no botão realmente dispara a ação. São 4 testes e você tem 4 certezas sobre o componente.

5 Semana 3 — APIs REST: O Backend que seu Frontend Consome

Entender o outro lado da comunicação • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Você já consome APIs. Agora vai entender como elas funcionam por dentro.

No seu dia a dia como dev frontend, você faz fetch("/api/usuarios") e recebe os dados. Mas o que acontece do outro lado? Quem decide que esse endpoint existe, quais dados retorna, e como valida o que recebe? Isso é o backend. E se sua meta é ser fullstack, você precisa entender os dois lados.

Uma API REST é um contrato de comunicação entre o frontend e o backend. É como um cardápio de restaurante: o cardápio lista o que está disponível (os endpoints), explica o que cada prato contém (os dados de retorno), e tem regras (não pode pedir sobremesa antes do prato principal, não pode pedir um prato que não existe). Quando o frontend faz uma requisição, ele está "pedindo um prato" — e o backend é a cozinha que prepara e entrega.

Os conceitos que você precisa dominar:

  • Verbos HTTP — Cada verbo diz o que você quer fazer. GET significa "me dê essa informação" (listar, buscar). POST significa "crie algo novo" (criar um usuário, enviar um formulário). PUT significa "atualize isso por completo" (substitui todos os campos). PATCH significa "atualize só essa parte" (muda só o nome, por exemplo). DELETE significa "apague isso". Você já usa isso no frontend com fetch — agora vai construir o lado que recebe essas requisições.
  • Status codes — São os "códigos de resposta" que o backend manda de volta. 200 significa "deu tudo certo". 201 significa "criado com sucesso". 400 significa "você mandou dados errados" (o frontend mandou algo inválido). 404 significa "não encontrei o que você pediu". 500 significa "erro no servidor" (o backend quebrou). Quando você sabe o que cada código significa, fica muito mais fácil debugar problemas de integração.
  • Validação de entrada — Nunca confie nos dados que chegam do frontend. Mesmo que o formulário tenha validação no lado do cliente, alguém pode mandar uma requisição direto pelo Postman (que você já usa!) pulando todas as validações. O backend sempre valida de novo: o email tem formato correto? O preço é um número positivo? O campo obrigatório foi preenchido?
Fase 2 — Exemplo Guiado: Criando uma API com Express + TypeScript

Você já tem Node.js nota 4. Vamos usar Express (o framework mais popular do Node) com TypeScript para construir uma API que o frontend poderia consumir:

// types.ts — define a forma dos dados (como uma interface React, mas para o backend)
export interface Tarefa {
    id: number;
    titulo: string;
    concluida: boolean;
    prioridade: "alta" | "media" | "baixa";
}

export type TarefaCreate = Omit<Tarefa, "id">;  // ← reusando Omit da semana 1!
// routes/tarefas.ts — os endpoints da API
import { Router } from "express";

const router = Router();
let tarefas: Tarefa[] = [];   // banco de dados em memória (só para aprender)
let proximoId = 1;

// GET /tarefas — listar todas
router.get("/tarefas", (req, res) => {
    res.json(tarefas);                           // ← retorna 200 automaticamente
});

// POST /tarefas — criar nova
router.post("/tarefas", (req, res) => {
    const { titulo, prioridade } = req.body;

    // Validação: nunca confie no que o frontend manda
    if (!titulo || titulo.trim().length === 0) {
        return res.status(400).json({              // ← 400 = dados inválidos
            erro: "O campo 'titulo' é obrigatório e não pode ser vazio"
        });
    }

    const nova: Tarefa = {
        id: proximoId++,
        titulo: titulo.trim(),
        concluida: false,
        prioridade: prioridade || "media",
    };
    tarefas.push(nova);
    res.status(201).json(nova);                  // ← 201 = criado com sucesso
});

// PATCH /tarefas/:id — atualizar parcialmente
router.patch("/tarefas/:id", (req, res) => {
    const tarefa = tarefas.find(t => t.id === Number(req.params.id));
    if (!tarefa) {
        return res.status(404).json({              // ← 404 = não encontrado
            erro: "Tarefa não encontrada"
        });
    }
    Object.assign(tarefa, req.body);
    res.json(tarefa);                            // ← 200 = atualizado
});

Perceba a conexão: a interface Tarefa usa os mesmos conceitos de TypeScript da semana 1. O PATCH usa Omit na prática. E os status codes (200, 201, 400, 404) são os mesmos que você já vê no DevTools do navegador quando debugga requisições no frontend.

6 Semana 4 — Code Review: Ler Código dos Outros (e Melhorar o Seu)

A habilidade mais subestimada da engenharia de software • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Por que ler código é tão importante quanto escrever?

No assessment, você disse que já recebeu code reviews, mas nunca fez um. Isso é normal no começo — geralmente alguém mais experiente revisa o seu código. Mas fazer code review é uma das formas mais rápidas de evoluir, porque te obriga a ler código que outra pessoa escreveu e pensar criticamente: "isso está claro?", "tem algum bug escondido aqui?", "tem uma forma mais simples de fazer isso?".

Pense assim: quando você só escreve código, você vê o mundo de um ângulo só — o seu. Quando você lê código de outra pessoa, você descobre formas diferentes de resolver o mesmo problema. Às vezes melhores que as suas, às vezes piores — e aprender a diferenciar é o que te torna uma profissional melhor.

O que olhar em um code review (checklist mental):

  • Funciona? — O código faz o que deveria fazer? Cobre os cenários normais e os edge cases? Se a API retornar erro, o componente trata isso ou quebra silenciosamente?
  • Está claro? — Outro dev consegue entender o que esse código faz sem precisar perguntar pra quem escreveu? Os nomes de variáveis e funções explicam o que fazem? Tem algum trecho confuso que deveria ser simplificado ou comentado?
  • Está seguro? — Os dados do usuário são validados antes de usar? Tem algum dangerouslySetInnerHTML sem sanitização? Informações sensíveis estão expostas no frontend?
  • Está consistente? — O código segue os padrões do projeto? Usa os mesmos nomes, a mesma estrutura de pastas, o mesmo estilo de componente que o resto do código?
  • Tem testes? — Se é uma feature nova, tem teste? Se é um bugfix, tem teste que impede o bug de voltar? (Conecta direto com a semana 2!)

Como dar feedback construtivo: Nunca diga só "isso está errado". Explique o que está errado, por que é um problema, e sugira uma alternativa. Em vez de "esse nome de variável está ruim", diga "o nome data não explica o que essa variável guarda — que tal listaUsuarios para ficar mais claro?".

Fase 2 — Exemplo Guiado: Revisando um componente React

Imagine que um colega mandou este componente para review. Leia com calma e tente encontrar os problemas antes de ver as anotações:

// UserList.tsx — componente enviado para review
export function UserList() {
    const [data, setData] = useState([]);        // ← sem tipagem, nome genérico
    const [x, setX] = useState(false);            // ← "x" não diz nada

    useEffect(() => {
        fetch("/api/users")
            .then(r => r.json())
            .then(d => setData(d));                // ← e se a API retornar erro?
    }, []);

    return (
        <div>
            {x && <p>Carregando...</p>}           // ← x nunca é setado para true!
            {data.map((u: any) =>                  // ← "any" desativa o TypeScript
                <div>{u.name}</div>               // ← sem key no map!
            )}
        </div>
    );
}

Review que você faria (feedback construtivo):

  1. Tipagem: data está como any[] e o map usa any. Sugestão: criar uma interface User e tipar o state como useState<User[]>([]).
  2. Nomes: data deveria ser usuarios. x deveria ser carregando ou isLoading. Nomes descritivos evitam que alguém precise ler o código inteiro pra entender o que cada variável faz.
  3. Tratamento de erro: Se a API retornar 500 ou a rede cair, nada acontece — o usuário fica numa tela vazia sem saber o que houve. Sugestão: adicionar um .catch() com estado de erro.
  4. Estado de loading: A variável x (que deveria ser isLoading) nunca muda de valor. Deveria ser true antes do fetch e false depois.
  5. Key no map: React precisa de uma prop key única em cada item de lista. Sem isso, a performance cai e podem acontecer bugs visuais quando a lista atualiza.

7 IA no Dia a Dia — Como Usar de Forma Inteligente

Vamos implementar Claude Code e ChatGPT como ferramentas do time. Mas existe uma progressão correta — não é "joga tudo pro AI e aceita o que vier".

1

Consumidor (Mês 1–2)

Você aprende a fazer perguntas básicas e usar as respostas. Nas atividades, você encontra prompts prontos para usar quando travar. Objetivo: quebrar a barreira do "não sei o que perguntar".

Exemplo: "Estou testando um componente React com Testing Library. Como simulo um clique em um botão?"

2

Colaborador (Mês 3–4)

Você formula seus próprios prompts com contexto: o que já tentou, qual o erro, o que espera. Exercícios incluem comparar prompts bons vs. ruins.

Exemplo: "Tenho um componente React que renderiza uma lista de 500 itens e está lento. Já tentei React.memo mas não resolveu. Quais outras otimizações posso tentar?"

3

Diretor (Mês 5–6)

Você sabe quando não confiar no AI. Consegue identificar respostas subótimas, corrigir sugestões, e usar a IA para acelerar — não para substituir seu raciocínio.

Exemplo: "O ChatGPT sugeriu usar useEffect para derivar um valor de outro state, mas isso causa re-render desnecessário. Vou usar useMemo em vez disso."

Regra de ouro:

Se você não consegue explicar por que o código que a IA gerou funciona, você ainda não entendeu. Volte ao fundamento e tente de novo.
