3 Semana 1 — Refatoração: De "funciona" para "bem feito"

Diretamente ligado à sua maior dificuldade • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: O que é refatoração?

Imagine que você tem um quarto bagunçado. Tudo funciona — suas roupas estão lá, seus livros estão lá — mas encontrar algo demora, e se outra pessoa precisar pegar algo, não vai saber onde está. Refatoração é arrumar esse quarto. O quarto continua tendo as mesmas coisas (o código continua fazendo a mesma coisa), mas agora está organizado.

Quando refatorar, você olha para 3 coisas:

  • Legibilidade — Se outro desenvolvedor abrir seu código amanhã, ele consegue entender o que cada parte faz sem precisar te perguntar? Se a resposta for "não", o código precisa ser mais claro.
  • Manutenibilidade — Se você precisar mudar uma regra de negócio (por exemplo, mudar o formato de validação de email), dá para fazer isso mexendo em um lugar só? Ou você vai precisar caçar essa lógica em 5 arquivos diferentes?
  • Simplicidade — Tem trecho de código que aparece copiado e colado em vários lugares? Tem funções gigantes que fazem 10 coisas ao mesmo tempo? Tem variáveis com nomes genéricos como data ou x que não dizem nada sobre o que guardam?

Sinais de que um código precisa de refatoração (chamados de "Code Smells" — literalmente "cheiro ruim no código"):

  • Uma função que tem mais de 30 linhas — provavelmente está fazendo coisas demais e deveria ser dividida em funções menores
  • Variáveis com nomes que não explicam nada: data, result, temp, x — troque por nomes que dizem o que guardam, como usuario, lista_produtos, email_validado
  • Blocos de código iguais que aparecem em mais de um lugar — se você precisa mudar essa lógica, vai ter que lembrar de mudar em todos os lugares (e vai esquecer algum)
  • Um único arquivo que faz tudo: recebe requisição, valida dados, acessa o banco, retorna resposta — como uma cozinha onde a mesma pessoa lava, corta, cozinha e serve ao mesmo tempo
Fase 2 — Exemplo Guiado: Refatorando uma API

Observe este código — funciona, mas tem problemas. Consegue identificar quais?

# ANTES: tudo junto, nomes genéricos, lógica repetida
from fastapi import FastAPI
app = FastAPI()

@app.post("/users")
def create(data: dict):
    if not data.get("name") or len(data["name"]) < 2:
        return {"error": "nome inválido"}
    if not data.get("email") or "@" not in data["email"]:
        return {"error": "email inválido"}
    # salva no banco... (imagina 50 linhas aqui)
    return {"ok": True}

@app.put("/users/{id}")
def update(id: int, data: dict):
    if not data.get("name") or len(data["name"]) < 2:   # ← repetido!
        return {"error": "nome inválido"}
    if not data.get("email") or "@" not in data["email"]:  # ← repetido!
        return {"error": "email inválido"}
    # atualiza no banco...
    return {"ok": True}

Problemas identificados: (1) validação duplicada, (2) nomes genéricos (data, create), (3) sem tipagem, (4) tudo no mesmo arquivo.

# DEPOIS: responsabilidades separadas, nomes claros, sem repetição

# schemas.py
from pydantic import BaseModel, EmailStr

class UserCreate(BaseModel):    # ← Pydantic valida automaticamente
    name: str
    email: EmailStr

# routers/users.py
from schemas import UserCreate

@router.post("/users")
def create_user(user: UserCreate):  # ← nome claro + tipado
    return user_service.create(user)

@router.put("/users/{user_id}")
def update_user(user_id: int, user: UserCreate):
    return user_service.update(user_id, user)

O que melhorou: validação em um lugar só (Pydantic), nomes descritivos, arquivo separado para schemas. Zero lógica repetida.

4 Semana 2 — Testes Automatizados com pytest

Garantir que o código funciona — e continua funcionando • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Por que testar?

Imagine que você corrige um bug na rota de criar usuário. Tudo funciona. Mas será que essa correção não quebrou, sem querer, a rota de atualizar usuário? E a de deletar? Você vai abrir cada uma e testar manualmente toda vez? Testes automatizados fazem isso por você em segundos. Você escreve o teste uma vez, e ele roda sozinho toda vez que você mudar alguma coisa no código. Se algo quebrar, o teste avisa na hora.

A Pirâmide de Testes — 3 tipos, cada um com um papel diferente:

  • Testes Unitários (a base da pirâmide, onde você vai escrever mais) — Cada teste unitário pega uma única função e verifica se ela faz o que deveria. Por exemplo: "a função calcular_desconto(100, 10) retorna 90?". São testes rápidos de rodar (milissegundos cada), e você vai escrever muitos testes desse tipo — dezenas ou até centenas em um projeto. Eles formam a base da pirâmide porque são os mais numerosos.
  • Testes de Integração (o meio da pirâmide) — Aqui você testa duas ou mais partes funcionando juntas. Por exemplo: "quando eu chamo a rota POST /usuarios, ela realmente salva o usuário no banco de dados?". Esses testes são mais lentos de rodar do que os unitários (porque precisam conectar no banco, por exemplo), então você escreve menos testes desse tipo do que testes unitários. Mas eles são essenciais para garantir que as peças se encaixam.
  • Testes E2E (end-to-end) (o topo da pirâmide) — Testam o sistema inteiro, do começo ao fim, como se fosse um usuário real usando o software. Por exemplo: "o usuário abre o navegador, faz login, cria um produto, e o produto aparece na lista". Esses testes são lentos de rodar (podem levar minutos) e são mais difíceis de manter, então você escreve poucos testes desse tipo — só para os fluxos mais importantes.

Como escrever um teste — o padrão AAA (3 passos simples):

Todo teste segue a mesma estrutura, sempre nessa ordem:

  • Arrange (Preparar) — Primeiro, você monta o cenário. Cria os dados que vai usar no teste. Exemplo: "vou testar desconto de 10% num produto de R$100, então preciso dessas duas variáveis prontas".
  • Act (Agir) — Depois, você executa a ação que quer testar. Chama a função, faz a requisição, dispara o evento. Exemplo: "chamo a função calcular_desconto(100, 10)".
  • Assert (Verificar) — Por último, você verifica se o resultado é o que você esperava. Exemplo: "o resultado deveria ser 90.0 — se for diferente, o teste falha e avisa que algo está errado".
Fase 2 — Exemplo Guiado: Testando com pytest

Vamos ver como um teste funciona na prática. Primeiro, temos uma função simples que calcula desconto. Depois, escrevemos 3 testes para garantir que ela funciona em diferentes situações:

# Função que queremos testar
def calcular_desconto(preco: float, percentual: float) -> float:
    if percentual < 0 or percentual > 100:
        raise ValueError("Percentual deve ser entre 0 e 100")
    return round(preco - (preco * percentual / 100), 2)

# Testes
def test_desconto_normal():
    # Arrange
    preco = 100.0
    percentual = 10.0
    # Act
    resultado = calcular_desconto(preco, percentual)
    # Assert
    assert resultado == 90.0   # ← cenário feliz

def test_desconto_zero():
    assert calcular_desconto(100.0, 0) == 100.0  # ← edge case

def test_desconto_invalido():
    with pytest.raises(ValueError):  # ← testa o erro
        calcular_desconto(100.0, -5)

Perceba o que fizemos: escrevemos 3 testes, cada um testando uma situação diferente. O primeiro testa o cenário normal (desconto de 10% em R$100 — deveria dar R$90). O segundo testa um edge case, que é uma situação incomum mas possível (desconto de 0% — o preço deveria continuar igual). O terceiro testa uma situação de erro (desconto negativo — deveria dar erro, não um resultado absurdo). Com esses 3 testes, você tem 3 certezas de que a função funciona corretamente.

5 Semana 3 — TypeScript: Introdução para quem vem do Python

Expandindo para o frontend com tipagem • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Python tem type hints. TypeScript é o mesmo conceito, só que obrigatório.

Você já conhece Python, então vou explicar TypeScript como uma tradução do que você já sabe. No Python, você pode colocar "type hints" — aquelas anotações que dizem "essa variável é uma string" ou "essa função retorna um int". Mas no Python, essas anotações são opcionais: se você não colocar, o código roda do mesmo jeito. No TypeScript, é diferente: as anotações de tipo são obrigatórias. Se você tentar passar um texto onde era para ser um número, o código nem compila — o editor já mostra o erro antes de você rodar qualquer coisa. Isso parece chato no começo, mas na prática evita muitos bugs que você só descobriria em produção.

Veja como a mesma função fica nas duas linguagens — a lógica é idêntica, só muda a forma de escrever:

# Python (type hints opcionais — o código roda mesmo sem eles)
def somar(a: int, b: int) -> int:
    return a + b

// TypeScript (tipos obrigatórios — sem eles, o código não compila)
function somar(a: number, b: number): number {
    return a + b;
}

Fase 2 — Exemplo Guiado: Interfaces e Componentes React

Agora vamos ver como o TypeScript funciona junto com o React. No código abaixo, primeiro definimos a "forma" dos dados (usando interface, que é o equivalente ao BaseModel do Pydantic), e depois criamos um componente React que recebe esses dados já tipados:

// Definindo a forma dos dados (como um Pydantic model)
interface Usuario {
    id: number;
    nome: string;
    email: string;
    bio?: string;  // ← opcional (como Optional no Python)
}

// Componente React que recebe um usuário como prop
interface CardProps {
    usuario: Usuario;
    onEditar: (id: number) => void;
}

function UserCard({ usuario, onEditar }: CardProps) {
    return (
        <div>
            <h3>{usuario.nome}</h3>
            <p>{usuario.email}</p>
            {usuario.bio && <p>{usuario.bio}</p>}
            <button onClick={() => onEditar(usuario.id)}>
                Editar
            </button>
        </div>
    );
}

Perceba a conexão com Python: a interface no TypeScript faz o mesmo papel do BaseModel do Pydantic no Python — ela define a "forma" dos dados, ou seja, quais campos existem e de que tipo são. A diferença é que no TypeScript, se você esquecer de passar o campo email ou passar um número onde deveria ser texto, o editor já mostra o erro antes de você rodar o código. É como se o Pydantic rodasse automaticamente enquanto você escreve, em vez de só na hora de executar.

6 Semana 4 — Arquitetura Básica: Organizando um Projeto

A ponte entre "funciona" e "escalável" • Tempo estimado: 4–6 horas

Fase 1 — Fundamento: Separação de responsabilidades

Imagine uma cozinha industrial. Tem a bancada de preparo (onde cortam os ingredientes), o fogão (onde cozinham), a área de montagem (onde montam o prato) e a expedição (onde entregam pro garçom). Cada área tem uma função específica, e as pessoas de cada área só se preocupam com o seu trabalho. O cara que corta os ingredientes não precisa saber como o garçom serve a mesa. Se a bancada vira uma bagunça, o prato inteiro atrasa — mas pelo menos você sabe exatamente onde o problema está.

No código é a mesma ideia. Em vez de jogar tudo num arquivo só (o que seria como uma cozinha onde a mesma pessoa corta, cozinha, monta e serve), você separa o código em 4 camadas, cada uma com uma responsabilidade única:

CamadaO que ela faz (e só isso)Arquivo no projeto
Router (também chamado de Controller)É a "porta de entrada". Recebe a requisição HTTP que chega do cliente (por exemplo, "POST /usuarios"), e repassa para a camada de Service processar. O Router não faz lógica nenhuma — ele só recebe e entrega.routers/users.py
ServiceÉ o "cérebro". Aqui ficam as regras de negócio: validações, cálculos, decisões. Por exemplo: "o usuário pode criar mais de 5 pedidos por dia?" é uma pergunta que o Service responde. Ele não sabe como os dados chegam (isso é do Router) nem como são salvos (isso é do Repository).services/user_service.py
RepositoryÉ o "armazém". Essa camada só fala com o banco de dados: salvar, buscar, atualizar, deletar. Se amanhã você trocar de PostgreSQL para MongoDB, só essa camada muda — o resto do código nem percebe.repositories/user_repo.py
Schema (também chamado de Model)É o "contrato". Define a forma dos dados: quais campos existem, qual o tipo de cada um, quais são obrigatórios. No Python com FastAPI, você usa Pydantic para isso. É como um formulário que diz "nome: texto obrigatório, email: texto obrigatório, idade: número opcional".schemas/user.py

Por que separar em camadas? Porque se precisar trocar o banco de dados, você só mexe no Repository — o Service e o Router continuam funcionando sem mudar uma linha. Se precisar mudar uma regra de negócio, você só mexe no Service — o Repository e o Router nem ficam sabendo. Cada camada cuida do seu, e ninguém precisa saber dos detalhes da outra.

Fase 2 — Exemplo Guiado: Estrutura de projeto FastAPI

Veja como fica a organização de pastas de um projeto FastAPI separado em camadas. Cada pasta contém arquivos de uma única camada. O main.py na raiz só faz uma coisa: iniciar o app e registrar as rotas — ele não tem lógica nenhuma:

meu-projeto/
├── main.py              # só inicializa o app e registra routers
├── schemas/
│   └── product.py       # ProductCreate, ProductResponse
├── routers/
│   └── products.py      # @router.get, @router.post...
├── services/
│   └── product_service.py  # regras de negócio
├── repositories/
│   └── product_repo.py  # queries SQL / ORM
└── tests/
    └── test_products.py # testes da semana 2!

O caminho que uma requisição percorre (de ponta a ponta):

Cliente faz requisição → Router (recebe e repassa) → Service (aplica regras de negócio) → Repository (salva/busca no banco) → resposta volta o caminho inverso até o cliente

Pense assim: o pedido do cliente passa por cada camada como uma esteira de fábrica. Cada estação faz uma coisa, e o produto final (a resposta) volta pelo mesmo caminho. Se uma estação tiver problema, você sabe exatamente onde ir consertar.

7 IA no Dia a Dia — Como Usar de Forma Inteligente

Vamos implementar Claude Code e ChatGPT como ferramentas do time. Mas existe uma progressão correta — não é "joga tudo pro AI e aceita o que vier".

1

Consumidor (Mês 1–2)

Você aprende a fazer perguntas básicas e usar as respostas. Nas atividades, você recebe prompts prontos para usar quando travar. Objetivo: quebrar a barreira do "não sei o que perguntar".

Exemplo: "Estou refatorando esta função em Python. Quais code smells você identifica?"

2

Colaborador (Mês 3–4)

Você formula seus próprios prompts com contexto: o que já tentou, qual o erro, o que espera. Exercícios incluem comparar prompts bons vs. ruins.

Exemplo: "Tenho uma API FastAPI com N+1 queries no endpoint /usuarios. Já tentei eager loading mas o ORM não suporta. Quais alternativas?"

3

Diretor (Mês 5–6)

Você sabe quando não confiar no AI. Consegue identificar respostas subótimas, corrigir sugestões, e usar a IA para acelerar — não para substituir seu raciocínio.

Exemplo: "O Claude sugeriu usar global state aqui, mas isso viola o princípio de isolamento. Vou pedir uma alternativa com dependency injection."

Regra de ouro:

Se você não consegue explicar por que o código que a IA gerou funciona, você ainda não entendeu. Volte ao fundamento e tente de novo.
